Copy a password from Bitwarden or KeePassXC on Linux, paste it, and a few seconds later
the password manager wipes the clipboard, exactly as its settings promised. Then open
your clipboard history and the password is sitting at the top of the list. Neither tool
is broken. The clipboard manager took its own copy the moment you pressed Ctrl+C, and the
password manager's timer only ever clears the clipboard itself.

## The short answer

A clipboard manager records every change to the clipboard, so it has the password long
before the clear timer fires. The only thing that keeps passwords out of clipboard
history is a mark on the copy that says "don't keep this", set by the password manager
and checked by the clipboard manager. That mark exists on Linux. It is a clipboard format
called `x-kde-passwordManagerHint`, and whether you are protected comes down to two
questions: does your password manager set it, and does your clipboard manager honour it?

KeePassXC's desktop app and Bitwarden's desktop app set it. The Bitwarden browser
extension and `keepassxc-cli` do not. Klipper, CopyQ, GPaste 51.1, the Clipboard History
GNOME extension and cliphist honour it; the Clipboard Indicator extension does not, and
neither does our own Clipmer. The tables below have the detail, and the rest of the page
is about closing the gaps.

## How the secret hint works

On Linux a copy is not a block of text sent somewhere. The app you copied from announces
a list of formats it can provide, and whoever wants the content asks for one of them —
[the clipboard is a promise, not a copy](/blog/clipboard-managers-on-wayland#the-clipboard-is-not-a-buffer).
A password manager can add one more entry to that list: a format named
`x-kde-passwordManagerHint` whose value is `secret`. It carries no content. It is a label.

KDE added the check to Klipper in
[May 2018](https://phabricator.kde.org/R120:637cd0bf62e419b8038cb9b1565089fbd341ee7a):
if the hint is present, the copy is not inserted into history. Everything that honours
the hint today does the same thing. CopyQ's
[security page](https://copyq.readthedocs.io/en/latest/security.html) describes it as the
marker KeePassXC and KDE Wallet use; wl-clipboard 2.3, released in March 2026, added a
`wl-copy --sensitive` flag that sets it from a script; and GPaste 51.1 marks the passwords
it puts on the clipboard the same way.

Two things the hint does not do. It does not clear anything — the password manager's
timer still does that, and still only clears the clipboard. And it is advisory: a
clipboard manager that never asks for the format list, and only reads the text, never
sees it.

KeePassXC sets the hint in its clipboard code on every Unix copy, and has an open issue,
[#12700](https://github.com/keepassxreboot/keepassxc/issues/12700), for the fact that
`keepassxc-cli clip` does not: a maintainer explained that the CLI handles the clipboard
separately because it runs without an event loop, and the issue is still open. If you
copy passwords from scripts, that is the copy that leaks.

Bitwarden is split down the middle. The desktop app merged
[PR #15393](https://github.com/bitwarden/clients/pull/15393) in July 2025, which turns on
the arboard library's `exclude_from_history` option on Linux; arboard's documentation says
that option works by adding the KDE hint to the selection. A user on Bitwarden's forum
[reported](https://community.bitwarden.com/t/linux-prevent-passwords-from-being-stored-in-clipboard-manager-history/94231)
that desktop 2026.7.0 on Plasma keeps passwords out of Klipper. The browser extension
cannot do the same: browsers only let a page or extension write a handful of standard
types, and a tester in that thread found `ClipboardItem.supports("application/x-kde-passwordManagerHint")`
returns `false` in Firefox 159, with `navigator.clipboard.write` throwing for the type.
Bitwarden's own tracking issue, [#1047](https://github.com/bitwarden/clients/issues/1047),
is labelled "upstream" for the same reason. If you copy from the extension's popup, the
password goes into history on every clipboard manager, hint-aware or not.

GTK apps are the third gap, and it is the one that matters most on GNOME.
`x-kde-passwordManagerHint` is not a valid MIME type — it has no `type/subtype` shape —
and GTK 4 validates the format names it is asked for and refuses to serve any that fail.
A GTK 4 app can advertise the name but never deliver its value. A
[GNOME Discourse thread](https://discourse.gnome.org/t/why-validate-mime-types-when-responding-to-clipboard-requests-on-wayland/35631) from June 2026 asked for
the reasoning; the replies were that the Wayland protocol never defined what a "mime
type" string may contain, and that the right fix is a real sensitivity API in GTK rather
than a fake format. KeePassXC's
[#12696](https://github.com/keepassxreboot/keepassxc/issues/12696) proposes a parallel
`text/x-kde-passwordManagerHint` so GTK can see it; nothing has been decided.

Klipper is the reason the hint exists, and it is the reason we wrote
[one thing Klipper does that most don't](/blog/kde-plasma-clipboard-history-not-working#one-thing-klipper-does-that-most-dont).
CopyQ silently drops a marked copy, and its documentation explains how to store secrets
from browsers only, which is the safer of its two overrides.

GPaste is the one to check the version of. Its
[51.1 release](https://github.com/Keruspe/GPaste/blob/master/NEWS) on 20 October 2026
added "Recognise passwords other clipboard managers mark as secret, and take them off on
time", and its source names `x-kde-passwordManagerHint` as the only marker it knows. The
GPaste your distribution installs is almost certainly older:
[Ubuntu 26.04 packages 45.3](/blog/clipboard-history-ubuntu#option-2-gpaste).

The two popular GNOME extensions differ. Clipboard History checks the format list and
ignores a marked selection; the switch is on by default and its author labels it "known
potentially buggy", which is honest about the fact that a check on a format name is only
as reliable as the apps that set it. Clipboard Indicator asks the clipboard for a fixed
list of text and image formats and never looks at the rest, so it keeps every password.
Its answer is the "Excluded Apps" setting, which matches the focused
window's class at the moment of the copy: add your password manager's window class and
nothing copied while it is focused is recorded. That protects a KeePassXC copy, but not a
Bitwarden extension copy, because the focused window is the browser.

cliphist on Hyprland or Sway honours it indirectly. wl-clipboard 2.3's `wl-paste --watch`
sets `CLIPBOARD_STATE=sensitive` when the hint is present, and cliphist's `store` command
does nothing in that case. Older wl-clipboard never sets the variable, so the copy is
stored.

## What Clipmer does with a copied password

Honestly: it keeps it. Clipmer polls the clipboard's text through Electron's
`clipboard.readText()` and never asks for the format list, so a password copied from
KeePassXC or the Bitwarden desktop app lands in its history like any other copy. We have
said as much on the Plasma page linked above, and we are saying it again here. Reading
the hint means asking for the clipboard's formats rather than its text, and it is a gap
we know about.

What you can do with the entry once it is there:

- **Hide it.** Open the entry's **⋯** menu and choose **Hide**. It renders as a fixed row
  of dots in the list, is left out of search, and opens as *Masked* in the viewer until
  you press **Reveal**. It still pastes. This is free, and
  [hiding individual entries](/blog/hide-clipboard-secrets-screen-sharing#hiding-individual-entries)
  covers what it does and does not protect.
- **Delete it.** Same menu, with a confirmation step.
- **Clear history.** In **Settings**, under Danger zone. Entries filed into folders are
  kept — see [what clearing keeps](/blog/hide-clipboard-secrets-screen-sharing#what-clearing-keeps).

## Habits that keep passwords out of any clipboard history

None of these depend on the hint, which makes them the ones to rely on while the apps
above catch up with each other.

- **Autofill instead of copying.** The Bitwarden extension fills login forms directly, and
  KeePassXC has browser integration and Auto-Type. A password that never touches the
  clipboard cannot be recorded by anything.
- **Switch the history off before a password session.** Clipboard History has a private
  mode on **Super + Shift + P**; Clipboard Indicator has a private mode toggle in its
  menu; Clipmer's equivalent is hiding the entry afterwards. The password manager's timer
  does not remove an entry from a history, so this is the only way to keep one from being
  made in a tool that ignores the hint.
- **Keep the clear timer on anyway.** KeePassXC's **Clear clipboard after** is on by
  default at 10 seconds, under **Settings → Security**. Bitwarden's **Clear clipboard**
  is under **Preferences** in the desktop app and **Autofill → Additional options** in the
  extension. It protects the clipboard itself, which is what a stray Ctrl+V reads.
- **Keep the history short, or clear it on a schedule.** Klipper's history size goes down
  to 1; Clipboard Indicator can clear on an interval or on every boot; [clearing the
  clipboard on Linux](/blog/clear-clipboard-linux) covers the manual version for the rest.

## If you want no history at all

The zero-risk option is to not run a clipboard manager, and on Plasma to set Klipper's
history size to 1. You give up the thing you installed it for: the command from an hour
ago, the address you pasted twice, the snippet you reuse. For most people the better
trade is a short history, a password manager that sets the hint, a clipboard manager
that reads it, and the habit of hiding or deleting the entries that slip through.
[If you don't want a history at all](/blog/hide-clipboard-secrets-screen-sharing#if-you-dont-want-a-history-at-all)
goes through what that costs with each tool.
